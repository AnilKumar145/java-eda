# Lesson 4.5: Database Logging, Statement Profiling, and Pool Telemetry

---

## 1. Why Database Observability Matters in Production

In high-throughput enterprise systems (e.g., intensive care telemetry, pharmacy dispensing, payment processing), the **relational database is almost always the primary scalability bottleneck**.

When a microservice slows down from 20 ms to 3,000 ms, 90% of the time the root cause is:
- An unindexed table query performing a 5-million-row full table scan.
- An accidental N+1 query loop issuing thousands of queries per HTTP request.
- Connection pool exhaustion because connections are held open during slow external API calls.
- Lock contention where concurrent transactions wait on each other for row-level locks.

Without comprehensive **database observability** (SQL query logging, execution timers, pool telemetry, and audit trails), engineering teams fly blind.

## 2. Hibernate SQL Logging: Configuration & Trade-offs

During development and staging, you must inspect the actual SQL queries Hibernate generates to verify they are optimal.

### The Naive Approach: `hibernate.show_sql = true`
Many tutorials recommend setting:
```properties
# DO NOT USE IN PRODUCTION!
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
```
**Why this is dangerous in production**:
- `show_sql` prints directly to standard output (`System.out.println`), bypassing your logging framework (Logback/Log4j2).
- It cannot be filtered by log level (DEBUG vs INFO).
- It lacks thread names, timestamps, correlation IDs, and MDC context.
- Synchronous `System.out` calls introduce severe thread synchronization overhead under load.

### The Production Approach: SLF4J / Logback Configuration
Instead, configure Hibernate's dedicated loggers in `logback.xml` or `application.properties`:

```xml
<configuration>
    <!-- Log SQL statements generated by Hibernate at DEBUG level -->
    <logger name="org.hibernate.SQL" level="DEBUG" />

    <!-- Format SQL on multiple lines (development only) -->
    <logger name="org.hibernate.orm.jdbc.bind" level="TRACE" />
</configuration>
```

```properties
# application.properties (Spring Boot)
logging.level.org.hibernate.SQL=DEBUG
logging.level.org.hibernate.orm.jdbc.bind=TRACE
```

## 3. Bound Parameter Logging & PII Masking

When Hibernate logs SQL queries, parameter values are logged as question marks (`?`):
```sql
SELECT p.id, p.full_name FROM patients p WHERE p.mrn = ?
```

To see the actual values bound to those placeholders, enable `org.hibernate.orm.jdbc.bind` at `TRACE` level.

```
2026-10-06 14:02:11 [main] TRACE org.hibernate.orm.jdbc.bind - binding parameter [1] as [VARCHAR] - [MRN-84920]
```

### Critical Security Rule: HIPAA / GDPR Compliance
In healthcare and financial systems, query parameters contain sensitive **Personally Identifiable Information (PII)** and Protected Health Information (PHI) such as patient names, social security numbers, and diagnosis codes.
- **Never enable parameter TRACE logging in production environments!**
- Ensure application log aggregators (e.g., Datadog, Splunk, Elastic) mask sensitive fields to comply with regulatory standards.

## 4. Slow Query Detection & Threshold Watchdogs

In production, you cannot log every SQL query—doing so produces terabytes of noisy logs per day. Instead, you log only **queries that violate your latency threshold**.

```
[Incoming Query] ---> Start Timer
                     Execute Statement on Database
                     Stop Timer (Duration = 340 ms)
                            |
                     Duration > Threshold (100 ms)?
                            |
                 +----------+----------+
                 | YES                 | NO
                 v                     v
          [ALERT: SLOW QUERY]     [Silent / Discard]
          Emit WARN log with:
          * Execution Time (340 ms)
          * SQL Statement
          * Caller Stack Trace
```

### Intercepting Execution Duration via JDBC Proxy / AOP:
```java
long startNanos = System.nanoTime();
try {
    return statement.execute(sql);
} finally {
    long durationMs = (System.nanoTime() - startNanos) / 1_000_000;
    if (durationMs > SLOW_QUERY_THRESHOLD_MS) {
        logger.warn("SLOW QUERY DETECTED: took {} ms | SQL: {}", durationMs, sql);
    }
}
```

## 5. Connection Pool Telemetry: HikariCP MXBean Metrics

**HikariCP** is the default high-performance JDBC connection pool in Spring Boot and enterprise Java.

To detect connection starvation, HikariCP exposes real-time pool metrics via JMX (`HikariPoolMXBean`):

```
+--------------------------------------------------------------------------+
|                     HikariCP Connection Pool (Size = 20)                 |
+--------------------------------------------------------------------------+
|  Active Connections (18)       : Currently executing queries in threads  |
|  Idle Connections (2)          : Ready for instant checkout             |
|  Threads Awaiting Connection (7): BLOCKED waiting for connection release!|
|  Total Connections (20)        : Total pool capacity                     |
+--------------------------------------------------------------------------+
      CRITICAL WARNING: 7 threads blocked waiting for connections!
```

### Accessing Metrics Programmatically:
```java
HikariPoolMXBean poolMxBean = hikariDataSource.getHikariPoolMXBean();

int activeConnections = poolMxBean.getActiveConnections();
int idleConnections = poolMxBean.getIdleConnections();
int awaitingThreads = poolMxBean.getThreadsAwaitingConnection();
int totalConnections = poolMxBean.getTotalConnections();

if (awaitingThreads > 0) {
    logger.error("CONNECTION POOL STARVATION: {} threads waiting! Active: {}/{}",
                 awaitingThreads, activeConnections, totalConnections);
}
```

## 6. Connection Pool Leak Detection: `leakDetectionThreshold`

A **Connection Leak** occurs when a thread borrows a connection from the pool, but fails to close it (for instance, missing `try-with-resources` or an uncaught exception path).

If 20 requests leak a connection, a pool of size 20 is completely exhausted, causing the entire application to hang indefinitely!

### The Solution: HikariCP `leakDetectionThreshold`
```properties
# Warn if a connection is not returned within 5,000 milliseconds
spring.datasource.hikari.leak-detection-threshold=5000
```

When a thread holds a connection longer than 5 seconds, HikariCP logs a stack trace showing exactly where the connection was checked out:
```
java.lang.Exception: Apparent connection leak detected
    at com.ead.service.PatientService.generateReport(PatientService.java:87)
    at ...
```

## 7. JPA Auditing: Automated Timestamping & Versioning

In enterprise software, every record mutation must be audited for compliance:
- Who created this row, and when?
- Who last modified this row, and when?
- What version is this row (optimistic locking)?

### JPA Entity Auditing:
```java
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class AuditableEntity {

    @CreatedDate
    @Column(name = "created_at", nullable = false, updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    @Column(name = "updated_at", nullable = false)
    private LocalDateTime updatedAt;

    @Version
    @Column(name = "version")
    private Long version; // Enables Optimistic Locking!
}
```

Whenever an entity subclass is persisted or updated, Hibernate automatically injects timestamps and increments the version counter without manual developer intervention.

## 8. Production Diagnostics Runbook: Starvation vs Lock Contention

When diagnosing database health under incident conditions, follow this triage flow:

```
Step 1: Check Pool Awaiting Threads
        * If awaitingThreads > 0:
          -> Are connections leaking? (Check leak logs)
          -> Are slow queries holding connections? (Check slow query log)
          -> Is pool size too small for CPU core count?

Step 2: Check Database Server CPU & Lock Waits
        * Run: SELECT * FROM pg_stat_activity WHERE state != 'idle';
        * Look for queries in 'waiting' state -> Indicates row-level lock contention!

Step 3: Analyze Query Plans
        * Run: EXPLAIN ANALYZE <slow_sql>;
        * Look for "Seq Scan" (Full Table Scan) on large tables.
        * Add targeted B-Tree composite indexes to eliminate table scans!
```
